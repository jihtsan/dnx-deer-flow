Architecture research / evidence-backed recommendation

不要把 n8n 控制能力塞进 DeerFlow。建立独立控制面，让两者保持各自运行时边界。

推荐形态不是再造一个庞大的第三套平台，而是一个可独立部署的模块化控制面：统一身份、策略、模型目录、知识目录、密钥引用、审计与动作目录；DeerFlow 继续负责对话与 Agent，n8n 继续负责确定性工作流与连接器执行。

执行摘要

最终建议是逻辑与部署上独立、产品体验上统一。控制面可以放在同一个 monorepo、走同一个 Nginx 域名、复用同一个前端壳和 SSO，但不能让 DeerFlow Gateway 成为 n8n 的配置数据库或总控进程。

核心判断： DeerFlow 与 n8n 是两个执行引擎，不是两个页面。中间层应当管理“谁能用什么能力、以什么成本和数据范围去执行”，而不是接管两边内部的线程、节点、队列、凭据表和迁移。

统一能力

身份与租户、跨系统权限策略、模型目录与预算、知识目录与 ACL、密钥引用、动作目录、审计与成本。

共享但隔离

Postgres 集群、Redis 服务、对象存储、向量数据库、可观测平台。共用产品，隔离数据库、schema、账号、key 前缀与生命周期。

运行时独占

DeerFlow 线程与 checkpoint、n8n workflow/execution/credential、n8n Bull 队列、DeerFlow sandbox 和 middleware state。

三种方案比较

在你已经明确“后期 DeerFlow 会调用 n8n、还要统一模型、知识库和权限”的前提下，独立控制面的长期收益明显高于初期多一个服务的成本。

不推荐

融入 DeerFlow Gateway

2.6 / 5
  • 短期页面和 API 开发最快。
  • 让 Python Agent 运行时承担 n8n 管理职责。
  • 扩大 Agent 工具执行面被攻破后的权限半径。
  • 未来接入第三个执行引擎时再次拆分。
推荐

独立控制面 + 双适配器

4.7 / 5
  • 控制面只保存策略、映射和目录，不保存两边内部状态。
  • DeerFlow 与 n8n 可独立升级、扩缩容和故障隔离。
  • 可以统一入口和前端，不必做成三个割裂产品。
  • 适合后续多租户、审计、预算和更多执行引擎。
不推荐

让 n8n 充当总控制面

2.4 / 5
  • 编排工作流很强，但不是企业权限或模型治理系统。
  • 模型和知识配置绑定在 workflow node 与 credential。
  • 把策略写进工作流会导致版本、审计与复用困难。
  • 产品授权和 Enterprise 功能边界会反向约束架构。

评分按边界清晰度 25%、安全与权限 25%、演进性 20%、运维隔离 15%、初期交付速度 15% 加权，属于架构判断，不是性能基准。

推荐目标架构

采用控制面与数据面分离。控制面决定策略与映射；运行时执行请求；模型网关、知识服务和基础设施属于可共享数据面。高频运行请求不必全部穿过控制面，只需携带它签发的短期授权与策略快照。

中间层到底要放什么

中间层只拥有跨 DeerFlow 与 n8n 的业务身份、策略、目录、映射和审计。判断标准很简单：凡是回答“谁可以用什么能力、用哪些数据、花多少预算、调用结果如何关联”的内容放中间层；凡是回答“Agent 或 Workflow 内部如何执行”的内容留在各自运行时。

一句话边界： 中间层保存控制关系和执行索引，不复制 DeerFlow 的对话状态，也不接管 n8n 的 Workflow、Credential、Execution 和队列。

模型配置怎么统一

统一的是“逻辑模型、路由策略、能力标签、预算和凭据来源”，不是把 DeerFlow 的 LangChain provider 配置和 n8n 的 node credential 强行压成一张表。

当前 DeerFlow 已具备的接口

  • config.yaml.models[] 是系统模型允许列表，模型 provider 使用可解析的 Python class path。
  • Gateway 公开只读模型列表，敏感 provider 字段不会返回前端。
  • 每次 run 可通过 context.model_name 选择模型，并在创建 run 前校验允许列表。
  • 模型配置属于 request-time 热加载字段；数据库、stream bridge 等基础设施字段是 startup-only。
  • 自定义 Agent 还可以保存一个 model override，但最终仍由全局允许列表解析。

n8n 的本质差异

  • 模型选择通常保存在 workflow 的 AI node 参数中。
  • 供应商认证通过 n8n credential 对象引用；同一个 OpenAI credential 可复用到 Chat、Embeddings 等节点。
  • 模型列表可从 provider 账号动态加载，因此不是一个独立的全局模型注册中心。
  • 把所有 workflow 的 node JSON 当作模型治理入口会造成版本漂移和难以审计。

知识库怎么统一

知识库最适合成为独立共享数据面，因为它天然跨对话与工作流。但要统一的是文档、ACL、索引版本和检索合同，不能只让两边连同一个 vector DB。

当前 DeerFlow 的真实状态： 已经有单例 Knowledge Scope、文档目录、上传、可靠 ingestion worker、LightRAG 健康/上传/追踪/查询/删除客户端；但 query_data() 目前没有接入 lead-agent 对话运行链。现阶段知识能力主要是管理与摄取面，这正是抽出共享 Knowledge Service 的最佳时机。

控制面所有

  • Knowledge Base / Scope 元数据
  • tenant、owner、group、document ACL
  • embedding 与 chunk schema 版本
  • 数据源、保留、删除与重建策略

Knowledge Service 所有

  • 原文件持久化与 hash
  • ingestion job、重试、对账
  • 向量 / 图谱 / keyword 检索
  • ACL 过滤、引用与证据封装

运行时只消费

  • DeerFlow 按 run 注入授权后的证据
  • n8n 通过 HTTP/MCP 查询或发起摄取
  • workflow-local 临时向量库不得成为 canonical KB
  • 双方不直接修改对方 ingestion 状态

共享向量库必须锁定的合同

knowledge_query { tenant_id, actor_id, knowledge_base_ids[], query, retrieval_policy_id, top_k, token_budget, correlation_id } knowledge_evidence[] { document_id, chunk_id, version, score, citation, source_uri, acl_decision_id, content }

必须额外固定 embedding model/version、维度、chunker、metadata schema、tenant namespace、软删/硬删、重建与引用稳定性。否则“共用一个 PGVector/Qdrant”只是在共享技术债。

关于当前 LightRAG 单例

现有配置指向一个 operator-managed LightRAG 服务，Knowledge Scope 在数据库层是全局单例，且适配器不发送 workspace header。这适合单组织 MVP，不足以直接承担多租户平台知识面。多租户阶段应由 Knowledge Service 显式映射 tenant + knowledge_base 到隔离的 collection/workspace/deployment，并在检索前执行 ACL。

权限与密钥边界

统一身份并不等于统一用户表。控制面维护跨系统 entitlement；DeerFlow 和 n8n 各自维护最小本地身份与资源所有权检查。

DeerFlow 当前能力

  • 支持本地账号和 OIDC，角色模型主要是 admin / user。
  • 已有 resource:action 权限常量与 decorator。
  • 但当前所有已认证用户都会拿到全部权限常量，细粒度权限尚未持久化到用户记录。
  • 线程使用 owner check；知识文档和 scope 使用 owner-filtered repository。
  • MCP 配置修改单独要求管理员。

n8n 当前边界

  • 用户、project、workflow、credential 和 API key 权限属于 n8n 自己。
  • Scoped API key、custom role、external secrets、source control 等能力受 Enterprise/版本约束。
  • 非 Enterprise API key 可能拥有调用者完整能力，不适合下发给 Agent 或浏览器。
  • n8n credential 使用自身 encryption key，不应被当作通用 Vault。

推荐授权链

1. 登录IdP subject + tenant claim
2. 解析身份映射内部 actor / service identity
3. 策略决策resource + action + data scope
4. 签发授权短期 token / policy snapshot
5. 适配映射 DeerFlow user 或 n8n project identity
6. 本地校验owner / workflow exposure / credential scope
7. 审计记录 decision、run、cost、result
密钥原则： 控制面只存 secret reference，Vault 使用两套 workload identity。DeerFlow 获取它被允许的 gateway/MCP secret；n8n 获取它被允许的 credential secret。不要共享 n8n 的 N8N_ENCRYPTION_KEY，也不要让 DeerFlow Agent 读取 Vault 管理凭据。

DeerFlow 与 n8n 双向调用

DeerFlow 调 n8n

已知、稳定、生产级工作流优先走带认证的 production Webhook；需要让 Agent 发现和选择工具时，使用 n8n instance-level MCP 或 workflow-scoped MCP Server Trigger，并在控制面再做一层 allow-list。

1. Agent tool提交 logical action ID
2. Action Broker校验 tenant / actor / input schema
3. 解析绑定action version → webhook / MCP workflow
4. n8n创建 execution 并返回 ID
5. Worker执行连接器与业务流程
6. 回调 / 轮询归一化状态与结果
7. Agent获取受控结果与引用
  • REST API 用于工作流的管理、发布、查询与执行状态，不把 n8n 数据库当 API。
  • MCP execute_workflow 会快速返回 execution ID，并存在 5 分钟 MCP timeout；长流程必须异步化。
  • workflow-scoped MCP 的 /mcp* 是 stateful 连接，多 webhook replica 时需按官方要求固定到单一专用 replica。
  • 控制面记录 logical action 与 n8n workflow/version 的映射，避免 Agent 持有任意 workflow ID。

n8n 调 DeerFlow

n8n 使用 HTTP Request node 调 DeerFlow Gateway 的 thread/run API。控制面签发 service token、模型策略与知识范围；长 Agent 任务采用 submit + poll/callback，不让 n8n worker 长时间阻塞 HTTP 连接。

1. Workflow准备 prompt、业务上下文
2. Control Plane校验 agent / model / KB 权限
3. 签发上下文actor、tenant、policy、idempotency
4. DeerFlow Run API创建 thread/run
5. Agent Runtime模型、工具、知识检索
6. 状态归一化running / succeeded / failed / cancelled
7. Workflow继续后续节点或补偿

统一任务信封

orchestration_request { request_id, idempotency_key, correlation_id, tenant_id, actor_id, service_identity, target: { engine, capability_id, version }, policy: { model_policy_id, knowledge_scope_ids[], budget_id }, input, callback, deadline }

信封保存跨系统语义；DeerFlow run_id、thread_id 和 n8n execution_id 作为 adapter binding 保存，不互相替代。

建议落地路线

先统一合同和入口，再统一数据面。第一阶段不要动 n8n 内部表，也不要立刻重写 DeerFlow 的知识 ingestion。

阶段 1：边界与调用合同

建立独立 control-plane 服务、tenant/actor/service identity、action registry、idempotency 与 correlation ID。实现 DeerFlow → n8n production Webhook，以及 n8n → DeerFlow Run API 两个最小适配器。

阶段 2：模型控制面

定义逻辑模型 ID、能力与预算；引入 Model Gateway。DeerFlow 配置 alias 与 run allow-list；n8n 提供受控 workflow 模板和 gateway credential，避免散落 provider key。

阶段 3：知识服务化

在现有 DeerFlow LightRAG adapter 和 ingestion worker 外形成稳定 Knowledge API，补齐 KB ACL、query endpoint 与 agent retrieval 注入。n8n 只调用 ingestion/query API。

阶段 4：细粒度权限与审计

将 DeerFlow 当前 admin/user + all-permissions 模型升级为持久化 entitlement；与 n8n project/workflow binding 对齐。打通 decision、model cost、KB citation 和 workflow execution 审计。

阶段 5：多租户与规模化

按租户隔离 LightRAG/vector namespace、对象存储、Redis 与 DB 角色；根据吞吐拆分 Redis 和 Postgres failure domain。固定 n8n 版本、许可与 MCP feature gate。

MVP 可以暂缓的内容

  • 自定义 n8n node：先用 HTTP Request / Webhook / MCP，只有编辑器体验和强类型 credential 真正需要时再开发。
  • 复杂事件总线：先用数据库 outbox + callback，吞吐和多订阅者出现后再引入 Kafka/NATS。
  • 拆分多个控制面微服务：先保持一个 deployable，模块边界明确即可。
  • 让控制面代理所有实时 token stream：直接数据路径更稳，控制面只签发授权与记录 binding。

高风险反模式与开放问题

不要共享业务表n8n 使用 TypeORM 和自有迁移；DeerFlow 使用 SQLAlchemy/Alembic。跨表读取会在任一方升级时静默失效。
不要共享队列协议n8n Redis/Bull 只接收 n8n main 入队的 execution ID。DeerFlow 不应直接写 key 或伪造执行。
不要复制明文密钥n8n credential、DeerFlow env、MCP config 和平台 Vault 各有不同生命周期。统一 reference 与 broker，不统一明文存储。
不要让 Agent 任意执行 workflowinstance MCP 的 workflow 可见性与搜索能力不等于你的业务授权。必须再做 logical action allow-list。
不要把 vector namespace 当 ACLcollection 名称隔离不是授权。检索必须使用可信 tenant/actor 上下文和 metadata filter，并记录 decision。
不要双重调度同一任务同一个 schedule 只能有一个 owner。否则会重复执行、难以幂等和补偿。
不要忽略 n8n 许可内部业务使用与向客户提供白标/托管工作流的许可边界不同。客户自带 credential 或核心价值来自 n8n 时需单独评估。

实施前必须确认的 6 个问题

  1. 这是内部平台，还是客户可直接创建 workflow、提供第三方 credential 的商业产品？
  2. 首期是单组织，还是从第一天就需要 tenant / department / project 隔离？
  3. n8n 使用 Community、Business、Enterprise 还是 Cloud，准备固定到哪个版本？
  4. 知识库是全局一个、每租户一个，还是每项目多个？文档 ACL 是否需要到用户/组？
  5. 模型策略是用户自由选择、管理员允许列表，还是按任务自动路由？预算阻断发生在哪一层？
  6. 长任务的 SLA、取消、回调、重试和人工介入由哪个系统负责？

判断置信度原因
控制面应独立于 DeerFlow 与 n8n高两边的状态、迁移、执行与密钥生命周期均为独立系统合同。
模型目录可统一，原生配置不可直接统一高DeerFlow 是 provider config + run override；n8n 是 workflow node + credential。
知识服务适合共享高DeerFlow 已有外部 LightRAG adapter；n8n 官方支持 HTTP、MCP 和多种向量节点。
当前 LightRAG 可直接多租户复用低现有实现是单例 Scope、单 operator-managed workspace，没有 tenant workspace contract。
instance-level MCP 可作为主要 Agent 动作入口中官方能力完整，但有版本、可见性、5 分钟 timeout 与部署路由约束。
n8n Enterprise 能力可用未知取决于你的许可、部署方式和固定版本，必须在实现前验证。
