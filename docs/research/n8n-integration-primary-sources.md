# n8n integration evidence for a DeerFlow control plane

Research snapshot: 2026-07-14 (Asia/Shanghai). Sources are limited to n8n's official documentation and official GitHub repositories. The documentation checkout used for verification was `n8n-io/n8n-docs` commit [`27272a7`](https://github.com/n8n-io/n8n-docs/commit/27272a777d1139ba7b58ee802192a80d0ce1ce6b), dated 2026-07-13. n8n 2.x is changing quickly; version-qualified MCP and secrets behavior below must be checked against the exact deployed n8n version.

## Executive findings

1. **Treat n8n as a separate execution system behind a control plane, not as a DeerFlow module.** Its workflow state, credential encryption, migrations, queue protocol, worker lifecycle, RBAC, and licensing are n8n-owned contracts. Integrate through supported HTTP/MCP/node surfaces rather than its tables or Redis queue.
2. **Share infrastructure products, not application schemas.** A Postgres cluster, Redis service, object store, external secret vault, observability stack, and vector database can be common infrastructure, but each system should have separate databases/schemas, users/ACLs, Redis namespaces or logical DBs, buckets/prefixes, and migration ownership.
3. **The best common business components are identity/policy, model catalog, secret vault, knowledge catalog, audit/usage, and invocation registry.** n8n does not document a cross-product model registry or knowledge catalog. Its model selection is node configuration plus n8n credentials; its RAG support is a set of vector-store/embedding/retriever nodes.
4. **Use Webhook for stable runtime endpoints, REST API for n8n administration, and MCP selectively for agent discovery/execution.** Instance-level MCP is especially relevant for DeerFlow, but has version-qualified capabilities, per-user visibility, and workflow exposure controls that must not be mistaken for a full service-to-service policy layer.
5. **Licensing is an architecture gate.** Internal company use is generally allowed, but white-labeling/charging for hosted n8n or collecting end-user credentials for an n8n-backed product can require a commercial agreement.

## Invocation surfaces in more detail

### Recommended order

1. **Known production workflow:** invoke its authenticated production Webhook through the control plane.
2. **Agent tool discovery and controlled execution:** use n8n's instance-level MCP or a workflow-scoped MCP Server Trigger, with a dedicated n8n identity and an additional control-plane allow-list.
3. **Provisioning and lifecycle:** use the public REST API to create/update/publish/move workflows, list executions, and manage credential metadata.
4. **Inside n8n only:** `Execute Sub-workflow` is an internal reuse mechanism; it can load a workflow by database ID or JSON/file/URL and optionally wait for completion. It is not a service boundary for DeerFlow. [Execute Sub-workflow](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflow/) · [Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflowtrigger/)

The instance-level MCP `execute_workflow` tool returns an execution ID immediately. It supports only documented trigger/input forms, doesn't support multi-step forms or human-in-the-loop interactions, and, where multiple supported triggers exist, may use only the first. The separate synchronous `test_workflow` tool (available from v2.15) has a five-minute timeout. Long-running business workflows therefore need an asynchronous run contract in the control plane: `submit -> internal run_id -> poll/callback -> normalized result`, rather than holding a chat turn open. [MCP tools reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference/)

## What can safely be common

| Common component | Share? | Required boundary |
|---|---:|---|
| Identity provider | Yes | Federate both systems to the same IdP, but map identity into each product's native user/project model and enforce control-plane policy before invocation. |
| Policy/tenant registry | Yes, as control-plane source of truth | Do not equate a DeerFlow workspace with an n8n project by database join. Maintain an explicit mapping table and reconcile through APIs. |
| Model catalog and budgets | Yes | Catalog is canonical; adapters render DeerFlow provider config and n8n node/credential references. Never duplicate plaintext provider keys into the catalog. |
| External secret vault | Yes | Separate workload identities and vault paths; n8n Enterprise can reference secrets only from credential fields. Community needs credential provisioning or controlled overwrite mechanisms. |
| Knowledge/document catalog | Yes | One canonical document/ACL/tenant catalog; n8n workflows call its ingestion/query API. Keep vector-store collection IDs as opaque bindings. |
| Vector database | Conditionally | Separate collection/table namespace per tenant and knowledge base; lock embedding model, dimensions, chunk schema, metadata filters, deletion semantics, and re-index version. |
| Postgres server | Conditionally | Separate database/schema and role; independent backups/migrations/SLOs. No cross-system table access. |
| Redis service | Conditionally | Separate logical DB/key prefix and ACL where supported; no direct writes to n8n's Bull queues. Prefer separate Redis instances once failure domains or scale justify it. |
| Object store | Conditionally | Separate buckets/prefixes and IAM. n8n execution/binary lifecycle must not delete DeerFlow knowledge source files. |
| Observability/audit pipeline | Yes | Carry a common `tenant_id`, `actor_id`, `conversation_id`, `workflow_id`, and control-plane `run_id`; never log credentials or full sensitive payloads by default. |
| n8n application DB/schema | No | n8n/TypeORM exclusively owns it. |
| n8n credential store/encryption key | No | n8n exclusively owns it; integrate through vaults/APIs/credential IDs. |
| n8n Redis queue | No | Internal n8n runtime contract only. |

## Plan/licensing boundaries to preserve

- **Community/self-hosted baseline:** PostgreSQL, queue mode, Webhooks, built-in AI/vector nodes, unscoped public API keys, private/unverified community nodes, and n8n-native encrypted credentials. The docs do not mark every baseline feature with an explicit Community badge; this summary uses the absence of an Enterprise availability marker plus explicit non-Enterprise behavior, so confirm against the selected release artifact.
- **Paid plans excluding Community:** RBAC projects are available outside Community, with project/role counts varying by plan. Source control/environments is Business and Enterprise. Credential sharing is Business/Enterprise self-hosted and all Cloud plans.
- **Enterprise:** scoped API keys, external secret stores, custom roles, multi-main HA, worker UI, and external S3/Azure execution/binary storage are explicitly gated in the relevant docs.
- **Cloud:** free trial lacks the public API; verified community nodes can be enabled, but unverified npm nodes are unavailable; Cloud database and scaling choices differ from self-hosted.
- **License caveat:** technical availability is not permission to resell or white-label n8n. Product/legal review is required if customers operate workflows, supply their own third-party credentials, or pay for functionality substantially derived from n8n.

## Confidence and open verification items

- **High confidence:** queue/database ownership, Webhook behavior, REST authentication, credentials/encryption, external secrets, AI/vector composition, MCP node transport constraints, community-node risk, and Sustainable Use restrictions are directly stated by current official docs.
- **Medium confidence:** treating instance-level MCP and queue mode as Community-accessible. The current pages do not mark them Enterprise-only, but n8n plan packaging can change faster than architecture docs.
- Before implementation, pin an n8n version and license tier, then verify its `/api/v1` OpenAPI surface, enabled MCP tools, credential/project entitlements, and the exact model/vector nodes in that build.
